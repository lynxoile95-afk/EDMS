# EDMS هوشمند — بسته تحلیل و طراحی (نسخه ۱.۰)

> پروژه مرجع: **EDMS-AI** — سامانه مدیریت مدارک مهندسی با موتور هوشمند استخراج PDF و تولید خودکار Transmittal
> تاریخ: ۲۰۲۶-۱۰-۲۴ · وضعیت: طراحی پایه (Baseline Design) · زبان: فارسی، با اصطلاحات فنی لاتین

---

## ۱. این بسته چیست؟

این پوشه، طراحی کامل یک EDMS هوشمند است: از نیازمندی‌های شماره‌گذاری‌شده تا مدل داده اجرایی، الگوریتم تطبیق با MDL، موتور تولید Transmittal، قرارداد API، طراحی صفحه بازبینی DCC، امنیت و نقشه راه. خروجی برای دو مصرف نوشته شده است:

- **تیم فنی**: مستندات ۰۲ تا ۰۶ و `db/schema.sql` مستقیماً قابل پیاده‌سازی‌اند.
- **کارفرما / تصمیم‌گیرنده**: فایل‌های ۰۱، ۰۹ و ۱۰ مبنای تأیید دامنه، بودجه‌بندی و پذیرش هستند.

خلاصه یک‌صفحه‌ای ایده: MDL پروژه یک‌بار از اکسل بارگذاری می‌شود؛ کاربر PDF نقشه را می‌فرستد؛ موتور هوشمند کادر مشخصات (Title Block) را می‌خواند، کد مدرک و Revision را استخراج و با MDL تطبیق می‌دهد؛ اگر همه‌چیز قطعی بود، Transmittal با شماره یکتا، گیرندگان DDM و مهلت پاسخ ساخته و ارسال می‌شود؛ در غیر این‌صورت به صف بازبینی DCC می‌رود. هیچ مدرکی بدون «تصمیم قطعی قاعده‌محور» ارسال نمی‌شود.

## ۳. فرض‌های پایه (در صورت اختلاف، همین‌ها را اصلاح کنید)

| کد | فرض | اثر در طراحی |
|---|---|---|
| A1 | سیستم **از صفر (Greenfield)** ساخته می‌شود، نه افزونه روی محصول موجود | انتخاب آزاد پشته فنی؛ در نقشه راه گزینه «سوار بر محصول» هم تحلیل شده |
| A2 | PDFها خروجی نرم‌افزارهای CAD هستند و Title Block دارند؛ بخشی هم اسکن‌شده‌اند | معماری چندلایه استخراج (متن → OCR → VLM) |
| A3 | شماره‌گذاری مدارک از یک قاعده ثابت پروژه پیروی می‌کند (مثل `PRJ-DIS-TYPE-SEQ`) | جدول `numbering_rule` و پارسر کد مدرک |
| A4 | Revision از نوع حرفی/عددی/P-prefix است و ترتیب آن قابل تعریف است | `rev_scheme` در تنظیمات پروژه + `rev_seq` |
| A5 | مدارک محرمانه‌اند؛ پردازش AI پیش‌فرض **On-Premise** | Worker محلی + مدل VLM روی GPU داخلی؛ ابر فقط با تأیید صریح |
| A6 | احراز هویت از Active Directory سازمان (LDAP/Kerberos) | Keycloak به‌عنوان Broker |
| A7 | تقویم کاری: شنبه–چهارشنبه (پنجشنبه/جمعه تعطیل)، تاریخ نمایش شمسی | `work_calendar` + لایه Jalali |
| A8 | تعداد کاربران فعال هم‌زمان ۵۰–۱۵۰، حجم سالانه ۵–۱۵ هزار سند | سایزبندی «متوسط» در سند ۰۸ |

## ۴. تصمیمات معماری کلیدی (خلاصه ADRها)

| ADR | تصمیم | چرا |
|---|---|---|
| ADR-01 | **مونولیت ماژولار + Worker جدا** (نه میکروسرویس کامل) | تیم کوچک، تراکنش‌های سنگین MDL/Transmittal، هزینه عملیات پایین؛ مرزهای ماژول آمادهٔ جداسازی آینده |
| ADR-02 | **قاعده، نه مدل، تصمیم نهایی را می‌گیرد** | مدل زبانی احتمالاً خطا می‌کند؛ ارسال مدرک به کارشناس اشتباه، خطای فاجعه‌بار است |
| ADR-03 | **پردازش نامتقارن (صف) با الگوی Outbox** | آپلود دسته‌ای A0 سنگین است؛ درخواست HTTP نباید بلوکه شود؛ ارسال اعلان باید «حداقل یک‌بار» و idempotent باشد |
| ADR-04 | **ذخیره کامل شواهد استخراج** (متن خام، برش تصویر، bbox، نسخه مدل) | ممیزی، بازآموزی، پاسخ به اعتراض پیمانکار |
| ADR-05 | **PostgreSQL + JSONB** برای payload استخراج، **MinIO/S3** برای فایل | سادگی استقرار داخلی، پشتیبانی از جست‌وجو و نسخه‌بندی |
| ADR-06 | **دو دروازه انسانی در فاز ۱** (تأیید DCC + تأیید نهایی ارسال) | تا رسیدن دقت به آستانه، ریسک صفر خطای توزیع |

## ۵. آنچه در این بسته **نیست**

- کد پیاده‌سازی و UI اجرایی (درخواست شما «تحلیل و طراحی» بود؛ اسکلت پروژه در فاز ۱ نقشه راه ساخته می‌شود).
- قیمت‌گذاری و پیش‌فاکتور (خارج از دامنه این بسته؛ در صورت نیاز جداگانه تهیه می‌شود).
- تعهد دقت عددی مدل روی داده شما: اعداد دقت در سند ۱۰ «هدف» هستند و باید با مجموعه طلایی ۳۰۰–۵۰۰ نمونه واقعی خودتان اندازه‌گیری شوند.

---

## ۶. سؤال‌های باز که پاسخ آن‌ها طراحی را دقیق‌تر می‌کند

1. یک نمونه واقعی PDF از Title Block هر پیمانکار (۳ تا ۵ نمونه) — بدون این، ROI قالب‌ها را نمی‌توان قطعی کرد.
2. الگوی رسمی شماره‌گذاری مدارک و لیست Revisionهای مجاز پروژه.
3. ساختار فعلی MDL (فایل اکسل واقعی) برای تعیین نگاشت ستون‌ها.
4. آیا Project Server / MSP در سازمان هست؟ (برای به‌روزرسانی خودکار برنامه زمانی)
5. سیاست: Transmittal برای هر دیسیپلین جدا یا مشترک؟
